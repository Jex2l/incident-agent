# Decisions log

Running log of non-obvious choices made autonomously while building incident-agent, per the project's working rules (ask only when truly blocked; otherwise decide, record, continue).

## 2026-10-02 — Phase 0

- **External SSD for Docker/Ollama data.** Internal disk had only ~18GB free (228GB volume, mostly consumed by system data). User has a 1TB external SSD mounted at `/Volumes/JEX2L` with ~492GB free — this project already lives there. Decision: point Ollama model storage at `/Volumes/JEX2L/ollama-models` via `OLLAMA_MODELS` (exported by the Makefile for all `make` targets) and recommend the user set Docker Desktop's VM disk image location to `/Volumes/JEX2L/docker-data` (a GUI setting I cannot set programmatically). Documented in `.env.example` and `infra/preflight.sh`.
- **Default LLM model kept at `qwen2.5:7b`** per spec, configurable via `LLM_MODEL`. Machine has 16GB RAM / Apple M2 (Metal, no CUDA) which can run a 7B q4 model adequately via Ollama. Noted in preflight output: if RAM/disk pressure appears during eval runs, fall back to `qwen2.5:3b`.
- **uv preferred, pip fallback.** `make venv` uses `uv` if present (faster, better lockfile behavior) and transparently falls back to `python3 -m venv` + `pip` if not installed, so the project isn't blocked on one more missing tool.
- **kind cluster topology: 1 control-plane + 1 worker**, with hostPort mappings for Grafana (3000), Prometheus (9090), Alertmanager (9093), and the webhook receiver (8000) baked into `infra/kind/kind-config.yaml` — avoids needing `kubectl port-forward` running in the background for day-to-day demo use.
- **Phase 1 scripts stubbed, not implemented.** `infra/install-observability.sh` and `infra/deploy-app.sh` exist as clearly-labeled placeholders that exit 2 with a "not implemented yet (Phase 1)" message, rather than being half-built. `make up` will stop earlier at `preflight` anyway since Docker/kind/kubectl/helm are not yet installed on this machine.

## 2026-10-02 — Phase 1

- **Redpanda deployed as a plain single-node Deployment, not via the Redpanda Operator/Helm chart.** The operator brings its own CRDs and a cert-manager dependency, which is unnecessary weight for one dev-mode broker on a resource-constrained kind cluster. Uses `redpanda start --mode=dev-container` with `--overprovisioned` on the official image. The spec's "installed via Helm" requirement was read as applying to the Prometheus/Alertmanager/Grafana/Loki+Promtail observability stack specifically, which is Helm-installed.
- **Frontend runs its own background traffic generator** (an asyncio task calling the cart service every ~2s) instead of requiring a human to click through the UI. This gives Prometheus continuous baseline metrics so fault-injection deltas (error rate, latency) are visible without a manual load generator process.
- **Fault hooks built into cart/kafka-consumer app code now, used in Phase 2**: `FORCE_CRASH_ON_BOOT`, `MEMORY_BALLAST_MB`, `LATENCY_MS` on cart; `CONSUMER_DELAY_MS`, `CONSUMER_STOPPED` on kafka-consumer. Building these into the apps now means Phase 2's fault scripts can just patch a Deployment's env vars via `kubectl set env` rather than needing custom crash/leak code injected at fault time.
- **Kafka consumer lag is computed from real consumer-group offsets** (`KafkaConsumer.end_offsets()` minus `position()` per partition, summed) rather than a synthetic counter, so the `KafkaConsumerLagHigh` alert reflects genuine Kafka introspection.
- **ServiceMonitors/PrometheusRules don't carry the chart's release label**; instead `kube-prometheus-stack-values.yaml` sets `serviceMonitorSelectorNilUsesHelmValues/ruleSelectorNilUsesHelmValues: false` so Prometheus Operator picks up any ServiceMonitor/PrometheusRule cluster-wide. Simpler than threading Helm release labels through every manifest.
- **Grafana is installed once** (via kube-prometheus-stack) and Loki is wired into it as a second datasource via a labeled ConfigMap, rather than installing loki-stack's own bundled Grafana — avoids running two Grafana instances.

## 2026-10-02 — Phase 1 verification (live cluster)

Docker/kind/kubectl/helm were installed and Docker's VM disk relocated to the SSD (`/Volumes/JEX2L/docker-data`) by the user. Ran the full Phase 1 stack for real and fixed five bugs surfaced only by actually running it:

1. **Grafana OOMKilled on boot.** Its memory limit (192Mi) was too low for Grafana 13.x plus two sidecar containers (`grafana-sc-dashboard`, `grafana-sc-datasources`). Raised Grafana to 400Mi limit, Alertmanager to 256Mi, Prometheus to 1Gi, and gave the sidecars their own resource block, since Docker Desktop's VM actually has ~15GB available (not a reason to under-provision).
2. **Alertmanager config rejected at startup**: `undefined receiver "null" used in route`. kube-prometheus-stack's default rule bundle includes a permanently-firing "Watchdog" heartbeat alert routed to a receiver literally named `null` by convention; overriding `alertmanager.config.receivers` without keeping that entry breaks config validation. Added `- name: "null"` back to the receivers list.
3. **`deploy-app.sh` used `declare -A` (bash 4+ associative arrays)**, but macOS ships bash 3.2 by default (`/bin/bash`) for licensing reasons. Rewrote as a plain newline-delimited "name path" list piped through `while read`.
4. **`kafka-python` 2.0.2 is unmaintained and broken on Python 3.12** (`ModuleNotFoundError: No module named 'kafka.vendor.six.moves'`). Switched both kafka-producer and kafka-consumer to `kafka-python-ng==2.2.3`, the actively maintained fork with the same `import kafka` API — a drop-in replacement, not a rewrite.
5. **Kafka consumer crash-looped**: `KafkaConfigurationError: Request timeout (6000) must be larger than session timeout (10000)`. The client requires `request_timeout_ms > session_timeout_ms` (default 10000); mine was 6000. Raised to 20000.
6. **All Python services' logs were invisible** (`kubectl logs` showed nothing, even though the processes were working fine per their `/metrics`) because Python buffers stdout fully when it isn't a TTY. Added `ENV PYTHONUNBUFFERED=1` to all 5 Dockerfiles — necessary groundwork for Phase 3's log_search tool too.
7. **Loki has no kind hostPort mapping** (only Grafana/Prometheus/Alertmanager/webhook-receiver did), so `curl http://localhost:3100` failed from the host even though Loki was healthy inside the cluster. Fixed `verify-phase1.sh` to open its own `kubectl port-forward` for the duration of the check (self-sufficient regardless of kind-config), and added a NodePort(30100)/hostPort(3100) mapping to `kind-config.yaml` + `loki-stack-values.yaml` for direct access on future cluster creations (not retroactive — an existing cluster needs recreating to pick it up).

**Real result after fixes: `infra/verify-phase1.sh` passes 7/7** against the live cluster — pod health, Prometheus query, Loki query + real log content, and a manually-triggered `cache` scale-to-0 fault producing a `HighErrorRate` alert that reached the webhook receiver's JSONL log.

**Deferred**: kube-prometheus-stack's bundled default alert rules (e.g. `NodeClockNotSynchronising`) also reach the webhook alongside our 6 app-specific alerts. Harmless for Phase 1, but before Phase 4 wires the agent to this webhook, either disable `defaultRules` in the Helm values or have the agent filter to known `root_cause_hint`-bearing alerts, so the agent isn't triaging infra noise.

## 2026-10-02 — Phase 2: fault injectors

Built 6 fault injection scripts (`faults/{oom_kill,bad_deploy,cpu_throttle,kafka_lag,crash_loop,dependency_down}.py`) sharing `faults/lib.py`, each with `inject`/`reset`/`run` subcommands, writing ground-truth records to `evals/runs/`. `faults/run_all.py` runs all 6 end to end and is the Phase 2 acceptance check. Ran it for real against the live cluster repeatedly while debugging; found and fixed 5 more real bugs:

1. **Reset via `kubectl apply` silently failed to remove injected env vars.** Fault injection uses `kubectl patch`, which mutates the live object without updating its `last-applied-configuration` annotation. `apply`'s 3-way merge diffs last-applied vs. new-desired to decide what to *remove*, so a field added out-of-band by `patch` (e.g. `FORCE_CRASH_ON_BOOT`) is invisible to that diff and silently never gets stripped - the crash-looping pod kept crashing after "reset." Fixed by making every reset its own explicit `kubectl patch` with a `"$patch": "delete"` directive (or an explicit overwrite) rather than reapplying the pristine manifest. Added `lib.patch_deployment()` to document why.
2. **`PodOOMKilled` alert rule never fired**: the PromQL `and` operator requires *identical label sets* on both sides by default. `kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}` carries a `reason` label that `kube_pod_container_status_restarts_total` doesn't have, so the two sides never matched. Fixed with `and ignoring(reason)`.
3. **`cpu_throttle` fault made the pod un-Ready, so its fault never showed up anywhere.** The `LATENCY_MS` sleep in cart's middleware applied to *every* route including `/readyz` - but the readiness probe's timeout (1s) is shorter than the injected delay (1.2s), so the probe always timed out, the pod never went Ready, and the Service never routed traffic to the faulty pod at all. Fixed by exempting `/healthz` and `/readyz` from the injected delay (also switched `time.sleep` to `await asyncio.sleep` so it doesn't block the whole event loop). Separately, the injected CPU limit (`15m`) was so low that even Python/uvicorn's own startup couldn't finish before the *liveness* probe killed the container (`connection refused`, no logs at all) - raised to `80m`, still a genuine 3x throttle but survivable for startup.
4. **`kafka_lag`'s lag metric was never set at all** (not even a zero sample): kafka-python-ng only assigns partitions after `poll()` completes the join-group handshake, and the `CONSUMER_STOPPED` code path never polls - so `consumer.assignment()` stayed empty forever and `report_lag()` always hit its early-return. Fixed with an initial poll before entering the main loop.
5. **That initial single `poll()` call wasn't always enough** - after repeated group-membership churn (many pods cycling through the same `orders-consumer-group` during testing), the join/sync handshake sometimes needs several poll() rounds to settle (observed up to ~90s). Fixed by looping `poll()` until `assignment()` is non-empty or 60s elapses, and widened `kafka_lag`'s own detection timeout from 5 to 7 minutes to give this room.

**Real result after all fixes**: `faults/run_all.py` passes 6/6 in a single clean run (`oom_kill` 41s, `bad_deploy` 160s, `cpu_throttle` 183s, `kafka_lag` 242s, `crash_loop` 101s, `dependency_down` 175s). Evidence in `docs/evidence/phase2-fault-suite-output.txt` and `docs/evidence/phase2-ground-truth/`.

## 2026-10-02 — Phase 3: MCP tools

- **Bumped `mcp` from 1.1.3 to 1.9.4.** 1.1.3 (the originally pinned version) predates `mcp.server.fastmcp.FastMCP`, which only has the low-level `Server` API (manual `@list_tools`/`@call_tool` decorators, explicit stdio transport wiring). FastMCP's `@mcp.tool()` decorator is dramatically simpler for 4 tool servers and is now the SDK's standard high-level API, so upgraded rather than hand-rolling the low-level protocol.
- **kube_read's safety boundary is the live Kubernetes API server, not this code.** `get_restricted_api_client()` builds a client authenticated as the `incident-agent-reader` ServiceAccount's own minted token (via `kubectl create token`), not the admin kubeconfig identity used to mint it. `infra/rbac/role.yaml` grants only `get/list/watch` on `pods, pods/log, events, services, deployments, replicasets` - no secrets, no write verbs anywhere, scoped to a namespaced `Role` (not `ClusterRole`) since the target app only lives in one namespace. `tests/test_kube_read.py` proves this by calling `delete_namespaced_pod`/`patch_namespaced_deployment`/`list_namespaced_secret` directly through the *same* restricted client the tool uses and asserting the API server returns 403 - not that the tool's own code happens to lack a delete method.
- **Two real bugs found by testing against the live cluster, not caught by anything static**: Prometheus returns HTTP 4xx (not a 200-with-error-body) for invalid PromQL, and Loki returns a *plain-text* (not JSON) error body for invalid LogQL - both tools originally called `raise_for_status()`/`resp.json()` unconditionally and would crash instead of returning a graceful tool error. Fixed in both.
- **runbook_search lazily builds its SQLite index on first search** if `runbooks/runbooks.sqlite3` doesn't exist, rather than requiring a separate build step before the tool works. `python -m tools.runbook_search --build-index --force` forces a rebuild (e.g. after editing a runbook). Pulled `nomic-embed-text` (274MB) to the SSD (`OLLAMA_MODELS`) to exercise the real embedding path, not just the BM25 fallback - verified both modes work and rank the right runbook first for `oom_kill` and `kafka_consumer_lag` test queries.
- **Wrote 8 runbooks** (one per fault scenario's `root_cause_label`, plus general `high_error_rate`/`high_latency` ones) rather than the full 10-15 suggested in the repo-structure description - sufficient to make the tool meaningfully testable now; more can be added in Phase 8 without any code changes, since the index is just "whatever's in `runbooks/*.md`."

**Real result**: `pytest tests/` passes 27/27 against the live cluster (no mocks for kube_read/prometheus_query/log_search - these are real integration tests). All 4 tools also verified end-to-end through the actual MCP `call_tool` protocol path, not just as plain Python functions.

## 2026-10-03/04 — Phase 4: agent loop

Built the investigation loop end to end:

- **`agent/llm.py`**: `LLMProvider` abstract interface + `OllamaProvider` using Ollama's `/api/chat` with `tools=`, parsing `message.tool_calls[].function.{name,arguments}` and tracking `prompt_eval_count`/`eval_count` for token budgeting. Verified Ollama's tool-calling response shape with a direct curl test before building around it.
- **`agent/mcp_client.py`**: the agent calls tools *only* through real MCP client sessions (`stdio_client` + `ClientSession`, one subprocess per `tools/*.py` server) - never imports `tools/*.py` directly. This exercises the actual MCP protocol path, not just the underlying Python functions.
- **`agent/budgets.py` / `agent/schema.py` / `agent/prompts.py` / `agent/orchestrator.py`**: hard budgets (steps/tokens/wallclock), JSON-schema-validated output with bounded format-retry, and the investigation-method system prompt (alert → blast radius → metrics → logs → events → runbooks → hypothesis → verify).
- **`agent/webhook.py`**: FastAPI intake. Alertmanager now has a *second* `webhook_configs` entry pointing at `http://host.docker.internal:8010/webhook` (verified reachable from inside the kind cluster via a direct test) alongside the existing dumb `webhook-receiver` logger - the agent runs on the host, not in-cluster, since it needs `ollama`, local `kubectl`, etc. Alerts without our `root_cause_hint` annotation (kube-prometheus-stack's bundled defaults) are filtered out before investigation starts.

**Real bugs found by running this against the live cluster (not caught statically):**

1. **Ollama's default 120s httpx timeout was too short** for qwen2.5:7b on this hardware - a single turn with accumulated tool-result context can take well over 120s. Raised to 240s, and raised `AGENT_WALLCLOCK_TIMEOUT_S` default from 120s to 480s to match (120s wasn't even enough for one multi-tool-call turn, let alone a full investigation).
2. **A crashed background investigation vanished silently.** `asyncio.create_task()` in the webhook handler had no exception handling - an uncaught error (e.g. an LLM timeout) just disappeared into asyncio's default exception logging, leaving zero record that the incident was ever investigated. Fixed with a try/except in `_run_investigation` that always writes a result (using `inconclusive_result` on crash), plus a bounded retry (`MAX_LLM_ERROR_RETRIES=2`) around the LLM call itself inside the orchestrator loop so transient provider errors don't need to escape all the way to the top to be handled.
3. **Namespace conflation in `kube_read.py`**: `get_restricted_api_client(namespace)` used the *query* namespace (whatever the model passed, e.g. a hallucinated `"default"`) to also mint the ServiceAccount token - but the `incident-agent-reader` SA only exists in the `incident-agent` namespace regardless of what's being queried. This produced a misleading "service account not found" error instead of a clean 403. Fixed by decoupling: token minting always uses the fixed `NAMESPACE` constant; the `namespace` parameter only ever selects which resources to list. Also added the same `ApiException` → structured-error handling to `list_pods`/`list_events`/`list_deployments` that `get_pod_logs` already had, for consistency.
4. **Discovered via this session, not a code bug**: running qwen2.5:7b and a full kind cluster simultaneously on an 8-core M2 can spike CPU to 1700-2000% (severe multi-core contention), which caused real Kubernetes API server TLS handshake timeouts and knocked `cart`/`frontend`'s liveness probes into repeated restarts (clean `Exit Code: 0`, not crashes) until contention subsided. The system's own resilience mechanisms (tool-call error handling, budget timeouts, bounded retries) absorbed this gracefully - every investigation still produced valid, saved output - but it's a real hardware constraint worth knowing about, not something more code can fix. Noted for Phase 7's eval timing expectations.

**Infrastructure note**: mid-session, Docker Desktop's VM restarted on its own (wiped all containers) and the user separately asked to cap its memory at 6GB (landed at 7.75GB) and move Ollama's actual model storage to the SSD (the `OLLAMA_MODELS` env var only affects one-off CLI calls, not the already-running Ollama.app GUI server - fixed via Ollama's own Settings → Models location, which migrates existing blobs). Both `make up` and the full Phase 1-3 suites were re-verified clean after each disruption, proving the setup is genuinely reproducible from scratch rather than relying on hidden local state.

**Real result**: ran 3 distinct fault scenarios through the actual webhook → investigate → save pipeline with zero manual steps beyond fault injection: `oom_kill` (correctly diagnosed, `root_cause_label: oom_kill`, confidence 0.9), `crash_loop` and `dependency_down` (both correctly returned `status: inconclusive` when budget/infra issues limited evidence, each with real saved evidence rather than a crash or silent loss). Every run has a saved trace in `traces/` and result in `evals/runs/`. Evidence copied to `docs/evidence/phase4-incidents/` and `docs/evidence/phase4-traces/`.
